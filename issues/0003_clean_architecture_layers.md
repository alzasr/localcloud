## Суть задачи

Сейчас команда живёт целиком в одном месте: разбор аргументов, проверки,
вывод и сами действия перемешаны. Пока команд немного, это терпимо, но с
ростом числа команд и действий любое изменение начнёт задевать всё сразу.

Нужно зафиксировать разделение на слои и привести код в соответствие:
терминальный клиент отвечает за ввод-вывод, пользовательские сценарии — за ход
выполнения команды, бизнес-логика — за конкретные действия над окружением.
Поведение команд при этом не меняется.

## Критерии готовности

- [x] Правила разделения слоёв зафиксированы в документации проекта: назначение слоёв и направление зависимостей.
- [x] Ввод-вывод, справка, разбор аргументов и коды возврата находятся в слое адаптеров и не содержат бизнес-правил.
- [x] Команда `init` реализована как пользовательский сценарий, который вызывает действия бизнес-логики.
- [x] Бизнес-логика не печатает в консоль и не зависит от адаптеров и сценариев.
- [x] Поведение CLI не изменилось: справка, тексты сообщений и коды возврата прежние.
- [x] Каждый слой покрыт тестами; тесты, статические проверки и сборка проходят.

## Результат

Код разделён на три слоя: терминальный адаптер (`internal/adapters/cli`),
пользовательские сценарии (`internal/usecases`) и бизнес-логика
(`internal/domain/workspace`); зависимости направлены только внутрь —
адаптер знает о сценарии, сценарий о действиях, обратных зависимостей нет.

Команда `init` стала сценарием: адаптер разбирает аргументы и печатает
результат, сценарий проверяет каталог и запускает действие бизнес-логики,
а действие сообщает, что создание окружения не реализовано. Правила слоёв
описаны в README в разделе «Архитектура», схема каталогов обновлена.

Проверено: у каждого слоя свои табличные тесты, тексты сообщений, справка и
коды возврата совпадают с прежними (`go test ./...`, `go vet ./...`, сборка и
ручной прогон `init`, `init --help`, `help`, `version`).
