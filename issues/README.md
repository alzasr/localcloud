# Задачи (issues)

Каталог для ведения задач проекта в формате Markdown: одна задача — один файл.

> Правила также оформлены как локальный скил Cline:
> [`.cline/skills/issue-tracker/SKILL.md`](../.cline/skills/issue-tracker/SKILL.md).

## Имя файла

`NNNN_shortTaskName.md`

- `NNNN` — порядковый номер задачи из четырёх цифр: `0001`, `0002`, ...
  Номер выдаётся по порядку и не переиспользуется, даже если задача отменена.
- `shortTaskName` — краткое название задачи на английском в snake_case:
  только строчные латинские буквы, слова разделены символом `_`
  (`initialize_go_project`, `add_version_command`).
- Разделитель между номером и названием — символ `_`.

Пример: `0001_initialize_go_project.md`

## Ветка задачи

Для каждой задачи создаётся отдельная ветка, имя которой совпадает с именем
файла задачи без расширения `.md`:

| Файл задачи | Ветка |
|-------------|-------|
| `0001_initialize_go_project.md` | `0001_initialize_go_project` |

- Перед выполнением задачи переключиться в основную ветку, подтянуть
  изменения из `origin` и только затем создавать ветку задачи — она всегда
  ответвляется от самых свежих изменений:

  ```bash
  git switch main
  git pull --ff-only
  git switch -c 0002_add_version_command
  ```

- Вся работа по задаче ведётся в ветке задачи.
- При смене статуса задачи имя ветки не меняется.
- Задача готова к слиянию, когда все пункты критериев готовности отмечены.

## Коммит

Сообщение коммита начинается с имени ветки, затем через `: ` идёт краткое
описание на русском, что сделано в коммите:

```
0001_initialize_go_project: инициализация проекта, CLI и трекера задач
```

- Имя ветки в сообщении совпадает с текущей веткой задачи.
- Описание — короткое, на русском, без точки в конце.
- Префиксы вроде `feat:` или `fix:` вместо имени ветки не используются.
- Все изменения по одному запросу оформляются одним коммитом: файл задачи,
  код, тесты и документация входят в него вместе, дробить работу на несколько
  коммитов не нужно.
- Пока коммит не отправлен в `origin`, правки по тому же запросу вносятся в
  него же (`git commit --amend`), а не отдельным коммитом.
- При необходимости ниже добавляется тело коммита с деталями изменений.

## Структура задачи

1. Заголовок первого уровня: `# NNNN — Название задачи на английском`.
2. Блок метаданных:
   - **Статус** — `открыта`, `в работе`, `выполнена`, `отменена`;
   - **Приоритет** — `низкий`, `средний`, `высокий`;
   - **Тип** — `инфраструктура`, `функциональность`, `исправление`, `документация`;
   - **Создана**, **Завершена** — дата в формате `ГГГГ-ММ-ДД`.
3. **Суть задачи** — что и зачем нужно сделать. Описание бизнес-смысла и
   ожидаемого поведения, без глубоких технических деталей и без описания
   конкретных файлов и функций.
4. **Критерии готовности** — чек-лист проверяемых результатов. Пункты
   отмечаются `[x]` по мере выполнения.
5. **Результат** или **Заметки** — необязательный раздел: итог работы,
   принятые решения, ссылки на связанные задачи.
