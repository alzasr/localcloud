# Трекер задач в `issues/`

Единый формат ведения задач: один файл — одна задача, плюс индекс в
`issues/README.md`. Правила одинаковы для всех задач проекта.

## Когда применять

- пользователь просит создать задачу, оформить тикет или зафиксировать работу;
- нужно обновить статус, критерии готовности или итог существующей задачи;
- нужно добавить или поправить индекс задач.

Источник истины — `issues/README.md` проекта. Если правила там отличаются от
описанных ниже, действовать по проектным и предложить синхронизировать этот
скил.

## Имя файла

`NNNN_short_task_name.md`

- `NNNN` — порядковый номер ровно из четырёх цифр с ведущими нулями:
  `0001`, `0002`, ..., `0999`, `1000`;
- `_` — единственный разделитель между номером и названием;
- `short_task_name` — краткое название задачи на английском в snake_case:
  только строчные латинские буквы, слова разделены символом `_`, без
  пробелов и дефисов (`initialize_go_project`, `add_version_command`).

Пример: `issues/0001_initialize_go_project.md`.

Правила нумерации:

1. Новый номер = максимальный существующий номер в `issues/` + 1.
2. Номера не переиспользуются: отменённая задача сохраняет свой номер.
3. При смене статуса файл не переименовывается.

## Ветка задачи

Имя ветки совпадает с именем файла задачи без расширения `.md`:

- файл `issues/0002_add_version_command.md` → ветка `0002_add_version_command`;
- перед началом задачи обязательно переключиться в основную ветку и подтянуть
  изменения из `origin`: `git switch main && git pull --ff-only`
  (если основная ветка называется иначе, использовать её имя);
- ветка задачи создаётся только от обновлённой основной ветки, то есть от
  самых свежих изменений;
- вся работа по задаче (код, файлы задач, индекс) ведётся в этой ветке;
- имя ветки не меняется при смене статуса задачи и не переиспользуется.

## Коммит

Сообщение коммита содержит имя ветки и краткое описание на русском:

`0002_add_version_command: добавлена команда version`

- формат заголовка: `<ветка>: <что сделано>`; имя ветки идёт первым, без
  префиксов `feat:`/`fix:`;
- описание — короткое, на русском, по существу изменений, без точки в конце;
- детали (список изменений) при необходимости добавляются в тело коммита;
- коммит делается в ветке задачи, поэтому имя ветки в сообщении всегда
  совпадает с текущей веткой (`git branch --show-current`);
- все изменения по одному запросу пользователя оформляются одним коммитом:
  файл задачи, код, тесты и документация — вместе, без дробления на
  «сначала задача, потом реализация»;
- правки по тому же запросу до отправки в `origin` вносятся в существующий
  коммит (`git commit --amend`), а не новым коммитом.

## Структура файла

```markdown
# NNNN — English task name

- **Статус:** открыта
- **Приоритет:** средний
- **Тип:** функциональность
- **Создана:** ГГГГ-ММ-ДД
- **Завершена:** ГГГГ-ММ-ДД

## Суть задачи

1–3 абзаца: что и зачем нужно сделать, какое поведение ожидается и какую
пользу это даёт. Без глубоких технических деталей.

## Критерии готовности

- [ ] Проверяемый результат.
- [ ] Проверяемый результат.

## Результат

Необязательный раздел: что сделано, как проверено, принятые решения.
```

Готовый шаблон для копирования: [templates/task.md](templates/task.md).

### Метаданные

Допустимые значения:

- **Статус:** `открыта`, `в работе`, `выполнена`, `отменена`.
- **Приоритет:** `низкий`, `средний`, `высокий`.
- **Тип:** `инфраструктура`, `функциональность`, `исправление`, `документация`.
- **Создана**, **Завершена:** дата в формате `ГГГГ-ММ-ДД`.
  «Завершена» указывается только для статуса `выполнена`.

Язык: заголовок и имя файла — на английском, метаданные и текст — на языке
проекта (по умолчанию русский).

## Как писать «Суть задачи»

- Описывать смысл и ожидаемое поведение, а не реализацию.
- Не упоминать конкретные файлы, пакеты, функции, структуры данных и
  алгоритмы — они попадут в код и в критерии готовности.
- Не дублировать критерии готовности: суть отвечает на «зачем», критерии —
  на «как понять, что готово».

## Как писать «Критерии готовности»

- Формулировать результат, а не процесс: «проект устанавливается одной
  командой», а не «создать `go.mod`».
- Каждый пункт должен проверяться без чтения кода.
- Технические проверки (тесты, линтеры, сборка) допустимы, но одним общим
  пунктом и без перечисления команд.
- В выполненной задаче все пункты отмечены `[x]`.

## Порядок работы

### Создание задачи

1. Прочитать `issues/README.md` и список файлов `issues/*.md`.
2. Определить следующий номер по правилам нумерации.
3. Придумать `short_task_name`: 2–4 слова на английском в snake_case
   (слова в нижнем регистре через `_`).
4. Переключиться в основную ветку и подтянуть изменения из `origin`
   (`git switch main && git pull --ff-only`), затем создать от неё ветку
   `NNNN_short_task_name` и переключиться в неё.
5. Создать файл по шаблону, заполнить метаданные: статус `открыта`,
   приоритет, тип, сегодняшняя дата создания.
6. Написать «Суть задачи» и критерии готовности.
7. Добавить строку в индекс `issues/README.md`:
   `| [NNNN](NNNN_short_task_name.md) | English task name | статус |`.
8. Проверить результат по чек-листу и закоммитить все изменения по запросу
   одним коммитом.

### Обновление задачи

1. Переключиться на ветку задачи `NNNN_short_task_name`; если ветки ещё нет —
   сначала обновить основную ветку (`git switch main && git pull --ff-only`),
   затем создать ветку задачи от неё.
2. Внести изменения в файл задачи (статус, чек-лист, итог).
3. При завершении: отметить пункты `[x]`, добавить «Завершена», заполнить
   раздел «Результат».
4. Обновить статус в индексе `issues/README.md`.
5. Закоммитить все изменения по запросу одним коммитом в ветке задачи:
   `<ветка>: <краткое описание на русском>`.
6. Не удалять задачи, не менять их номера и имена веток.

## Чек-лист перед завершением работы

- [ ] Имя файла: `NNNN_snake_case_name.md`, номер ровно из четырёх цифр.
- [ ] Работа ведётся в ветке `NNNN_snake_case_name`, имя совпадает с именем
      файла задачи без расширения.
- [ ] Ветка задачи создана от основной ветки после `git pull --ff-only`.
- [ ] Сообщение коммита: `NNNN_snake_case_name: краткое описание на русском`.
- [ ] Все изменения по запросу вошли в один коммит.
- [ ] Заголовок `# NNNN — English task name` совпадает с индексом.
- [ ] Метаданные заполнены допустимыми значениями, даты в формате `ГГГГ-ММ-ДД`.
- [ ] «Суть задачи» без файлов, функций и прочих глубоких деталей.
- [ ] «Критерии готовности» — проверяемые пункты.
- [ ] Строка в индексе `issues/README.md` добавлена или обновлена.
- [ ] Markdown-файлы сохранены с LF-переводами строк.
